# 塑料实体存储的 26.1.2 迁移计划

## 当前决定

Minecraft 1.21.1 版本保留内部调试覆盖，可制造超过 `3x3x3` 的塑料实体；多相超限合金和内部调试覆盖也可按完整外接总体积赋予箱子、储罐等功能容量。此类实体可能具有非常大的槽位数、流体容量、体素掩码和内容数据，因此单个实体或物品的 NBT 可能明显增大。

这是当前版本有意接受的取舍：此类超限制品只能通过消耗内部调试资源产生，不为它们额外限制容量，也不在 1.21.1 临时引入一套只服务于迁移前版本的存储格式。当前版本仍需保持服务端校验、递归容器防护和网络包大小边界，避免恶意数据绕过既有上限。

## 26.1.2 迁移目标

迁移到 Minecraft 26.1.2 与对应 AnvilCraft 版本时，使用 AnvilCraft 26.1 铁砧工艺本体的新存储系统重新实现塑料实体的存储后端。塑料实体的类型、外形与玩法接口保持在 Plasticraft 边界内，实际内容存储、容量视图和持久化尽量复用本体公开 API，不复制本体内部实现，也不通过反射接入。

迁移重点如下：

1. 将箱子槽位和多流体列表从随实体完整展开的 NBT，改为本体存储系统支持的紧凑或外置表示
2. 区分客户端显示摘要与服务端权威内容，只同步已用格数、总容量、流体总量和当前浮窗需要的分页数据
3. 让物品能力、流体能力、Jade、铁砧锤浮窗和回收物品共用同一存储句柄，避免为不同入口复制全部内容
4. 为实体保存、区块卸载、跨维度移动、锤回物品和重新放置定义原子提交与失败回滚边界
5. 为超大空容器、稀疏内容、密集内容、多流体、嵌套容器拒绝和断线重连建立容量与网络压力测试
6. 保持注册名、资源路径、配方 ID 和现有网络载荷字段顺序稳定；新增数据通过清晰的新边界接入

## 兼容范围

当前项目只维护 1.21.1，不在本版本提前实现 26.1.2 存储适配，也不添加旧存档兼容或旧 NBT 读取逻辑。正式迁移时根据 26.1.2 的实际 API 单独确定数据转换策略；在用户明确要求前，不承诺把开发期 1.21.1 的超大创造制品直接转换到新格式。

## 验收基线

迁移后的可见容量和行为必须与当前规则一致。例如内部调试覆盖把实心 `100x100x100 px` 模型强制指定为箱子时仍为 `15625` 格，超限实体的外形、内容顺序、能力访问、回收与重新放置都不得丢失。优化目标是减少持久化与同步负担，不得用静默截断容量或内容替代存储优化。
