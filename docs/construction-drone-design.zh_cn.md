# 无人机与蓝图施工系统设计规格

> 状态：讨论稿 v8，尚未进入实现
>
> 适用版本：Minecraft 1.21.1 / NeoForge；为未来迁移到 26.1.2 保持数据、服务端逻辑和客户端渲染边界，不在当前版本加入旧存档迁移
>
> 核心结论：建设、拆除、收集与观察无人机使用普通实体模型和同一套工具化机械实体能力；任务采用“流体封堵与真实拆除 -> 掉落物回收 -> 真实取料与飞行 -> 带碰撞的施工投影 -> 完工或取消时安静提交”的阶段流程，不逐块运行目标方块逻辑，也不分析红石电路的施工依赖。任务主动建立的区块票只来自观察无人机，每架实际加载自身所在区块及水平相邻八个区块，共 `3 x 3` 个实体刻区块

## 1. 四类无人机、模型与工具扩展

建设无人机使用如下 `3x3` 有序合成：

```text
螺旋桨 飘升机 螺旋桨
空 磁电核心 处理器
蟹钳 电容器 空
```

其余三类无人机使用相同有序合成，只替换第三行的蟹钳位置：

```text
拆除无人机：切石机 电容器 空
收集无人机：手持磁铁 电容器 空
观察无人机：望远镜 电容器 空
```

四类无人机都不是方块模型，也不应继承当前的 `AbstractPlasticEntity`。后者以 `FallingBlockEntity` 为基础，包含重力、流体、磁力、粘合、滑轨和方块化等大量无人机不需要的物理语义。世界中推荐只注册一个普通机械无人机实体类型，建设、拆除、收集和观察是由已安装工具定义的四种物品变体；物品化、入库和铁砧锤回收后仍保持各自名称、工具、数据和库存。这样既保留玩家可辨识的四种无人机，也不会复制四套飞行、充电、避障和停泊代码。

工种不得写成实体类内不断扩张的 `switch`。实现时建立服务端 `DroneToolDefinition` 注册边界，每项至少声明稳定资源 ID、匹配的工具物品、支持的任务能力、触及距离、内部库存布局、能量报价、服务端动作执行器及需要同步的显示状态。当前注册项为：

| 无人机 | 已安装工具 | 当前能力 | 内部物品库存 |
| --- | --- | --- | --- |
| 建设无人机 | 蟹钳 | 取料、携带、施工投影交付、临时流体封堵 | 仅一份任务托管携带物，不作为普通库存 |
| 拆除无人机 | 切石机 | 瞬间真实拆除 | 无 |
| 收集无人机 | 手持磁铁 | 收取任务掉落物或自由拾取物品并卸载 | `9` 格 |
| 观察无人机 | 望远镜 | 加载自身所在区块及水平相邻八个区块，并在任务中引导机群 | 无 |

以后加入剪刀、钓鱼竿、打火机、刷子和护符盒时，只新增工具定义与对应任务执行器，分别提供剪羊毛、钓鱼、点火、考古和让附近玩家获得护符效果等能力，不改变无人机实体的保存格式、飞行器或渲染器。AnvilCraft 多用途工具以后作为一个复合工具定义，可以在领取任务时从其已声明能力中选择除拆除以外的任一动作；切换的是当前任务能力和显示姿态，不临时改写实体类型。切石机拆除保持独占能力，避免多用途工具绕过拆除阶段、掉落和权限规则。

模型使用 Blockbench 的 `Modded Entity`，导出为原版 `EntityModel/ModelPart` 风格，不为这一实体引入 GeckoLib。主体和工具附件是分离模型层，渲染采用混合方式：

- 机身、工具安装座、磁电核心和处理器外壳是共用实体模型部件；蟹钳、切石机、手持磁铁和望远镜全部使用 Plasticraft 风格统一的定制可动附件模型，通过工具定义选择对应附件层，不直接渲染配方输入物品的烘焙模型
- 两个螺旋桨不是烘焙进固定贴图的几何，而是分别保留合成输入的完整 `ItemStack`，通过现有 `MoldedPlasticMeshRenderer` 一类的动态塑料网格渲染能力显示
- 两个螺旋桨各自保留玩家制作的模型、颜色、材质和数据组件，不把两者合并成一个平均外观
- 任意一个螺旋桨具备某种材料特性，整架无人机就获得该特性；例如任意一侧是耐热塑料螺旋桨，整架无人机即可防火。后续特性使用材料能力集合做并集，不在无人机类内逐种硬编码
- 螺旋桨在飞行和悬停时连续旋转，转速只读取实体同步的运动/工作状态；渲染器不决定服务端行为
- 蟹钳具有张开、接近、抓取、持物和释放动画。抓住物品时的姿态与铁砧工艺配方中“副手持蟹钳拿着物品”的渲染保持一致，公共持物姿态应只有一份定义
- 蟹钳内显示真实携带的方块物品、桶、树脂捕获物、船等 `ItemStack` 模型，不制作一套重复的假贴图
- 拆除无人机显示定制切石机附件而不显示蟹钳，不具有抓取或持物状态；刀片与机架只表现瞬间拆除动作，不引入持续挖掘进度
- 收集无人机显示定制磁铁附件；附件动作和九格库存摘要只读取服务端同步状态，客户端不能自行决定或提前移除掉落物
- 观察无人机显示定制望远镜附件，并在选定加载位置伸出镜筒朝任务方向观察；望远镜朝向只是工作状态表现，不参与加载覆盖判定
- 四种无人机物品在所有物品显示环境中调用同一套实体渲染管线，使用物品数据内的两个真实螺旋桨和对应附件；物品形态与实体形态不能出现不同的简化外观

实体碰撞箱固定为 `0.5 x 0.5 x 0.5` 方块。螺旋桨、已安装工具和携带物可以超出碰撞箱并发生视觉穿模；“一格八架”指八个自由实体碰撞箱可以在一格空间中堆放，不是无人机站内部的八分之一格泊位。无人机之间保留实体碰撞和推动，飞行时用避让与路线预约尽量避免真正撞上；停机时可以被玩家推动、被踩踏并互相堆叠。

四类无人机只继承三项塑料实体体验：

1. 对玩家和其他实体提供可站立的硬碰撞
2. 参与实体推动，且被推动后不会穿过方块或其他硬实体
3. 被铁砧锤回收为对应工具变体物品，完整保留两个螺旋桨、工具、能量、设置、所有者、收集库存和任务恢复所需数据

无人机实体右击打开单机设置界面；手持无人机物品时潜行右击打开同一设置界面。公共界面显示工具能力、能量、所有者和状态，建设/拆除类还显示缺料与缺拆除能力策略，收集类显示九格库存，观察类显示区块加载状态。策略默认为“暂停等待”，另一个选项为“跳过”；它处理建造或临时填充材料不足以及缺少拆除无人机。收集无人机是可选优化，缺少观察无人机则按区块可用性等待；二者不套用“跳过”。没有权限的方块始终强制暂停，不能由任何配置绕过。无人机站界面统一设置其内部无人机；被远程借调的无人机执行任务期间遵循目标任务站的策略，返回原站后恢复原站配置。

无人机进入站点时先从上方对准顶部泊位；到位后服务端把完整数据原子转入站内槽位并移除有碰撞实体，客户端再以无碰撞停泊显示对象播放开门和下沉动画。离站时先从站内槽位原子转入无碰撞出库显示对象，升出并确认生成位置无碰撞后才生成真实实体。站点本体因此始终使用稳定方块碰撞，不为舱门临时打开可供玩家或其他实体进入的洞口。实体、物品与停泊显示对象之间不得丢失工具、材质特性、能量、设置、来源站、所有者、任务托管物或收集库存。拆除和观察无人机永远没有携带物槽；拆除无人机不会吸取、收集或转运被拆方块的掉落物。

## 2. 蓝图、结构磁盘与中央施工任务

一个已经放到世界中的蓝图对应一个服务端权威 `ConstructionJob`。蓝图保存“要建什么和放在哪里”，任务保存“谁在建、资源从哪里来、流体封堵与拆除进度、任务生成的掉落物、哪些操作已交付、哪些被跳过以及当前提交状态”。无人机只持有短期分配，不把整份蓝图复制进每架无人机。

蓝图默认只放置投影而不启动。一个玩家可以放置任意数量的蓝图，但同一时间最多启动一份；启动新蓝图会暂停该玩家先前启动的蓝图。这个限制是“每名玩家一个活动任务”，不是全服务器只能有一份任务。非活动蓝图只保存和渲染必要信息，不保持区块加载，也不吸引无人机。

无人机和无人机站归制造或放置玩家所有，只参与所有者或同一 FTB Teams 团队成员的任务。FTB Teams 支持放在独立可选集成类中，通过其公开 API 查询当前团队关系，公共任务入口不直接初始化 FTB Teams API；未安装 FTB Teams 时退化为仅所有者授权。不同所有者且不在同一 FTB Teams 团队的活动蓝图不能争抢无人机，远程转运、自由收集卸货和任务材料访问也不能越过该边界；权限检查属于服务端任务分配条件，不由客户端 GUI 决定。团队成员变化后在下一次派发、卸货或世界交互前重新校验，不能把已经离队的授权永久缓存进无人机 NBT。

蓝图在世界中的部署、锚点移动、旋转、镜像、确认和分层投影交互以 Create 蓝图体验为基准，使用 Plasticraft 自己的贴图、颜色和状态表现，不照搬 Create 美术资源。结构磁盘只改变蓝图数据和任务状态，不把 Create 作为运行依赖。

结构磁盘与部署任务之间使用稳定的任务 UUID 和蓝图内容哈希关联。已经部署的结构磁盘在任何能够容纳它的菜单槽中都按任务状态由程序直接绘制纯色槽底：黄色表示未启动，绿色表示已启动，不读取专用槽位贴图。右击该磁盘槽会覆盖该槽原有的拿取、拆半或快捷交互，直接启动对应任务并暂停玩家的其他任务；启动没有按钮或图标。槽底属于 `ItemStack` 的客户端显示状态，因此磁盘移动到玩家背包、箱子或其他菜单槽后仍跟随磁盘。无人机站内需要一个独立任务磁盘入口；磁盘进入后会直接启动对应任务、暂停所有者的其他任务，并使该站立即成为唯一协调站。

站点认领任务后：

- 附近无站建设、拆除和观察无人机都退出该任务，无站建设无人机不再从玩家身上取料；无站收集无人机继续执行自己的 `16` 格自由拾取模式，不领取中央任务租约，但仍可像玩家或漏斗一样独立拿走范围内掉落物，任务台账把这部分记为外部结算
- 已经取料的无站无人机先回到来源玩家身边返还物品，再退出任务
- 本站和远程调来的无人机都只从任务站下方物流库存取得蓝图材料与临时流体填充块；任务掉落物由收集无人机送回任务站指定卸载端
- 磁盘离开任务站或任务被暂停时停止继续派发，已在途资源按任务台账返还；玩家显式取消则执行第 3 节的按进度提交

任务至少具有以下状态，状态转换只由服务端完成：

| 状态 | 含义 |
| --- | --- |
| `INACTIVE` | 投影已放置但未启动，不派发、不加载整个蓝图区域 |
| `PLANNING` | 解析结构、扫描原有方块与流体、生成拆除/材料/观察点清单并复核权限和可达顺序 |
| `WAITING_PERMISSION` | 任一计划操作被领地或权限系统拒绝；不允许按“跳过”继续，等待权限恢复或玩家取消 |
| `WAITING_OBSERVER` | 下一项所需区块没有其他实体刻级加载来源，且暂时没有观察无人机能够建立连续的九区块覆盖窗口 |
| `SEALING_FLUID` | 建设无人机真实放置临时填充块，一次封堵计划范围内会再生或回流的流体片区 |
| `DEMOLISHING` | 拆除无人机按切石机砸击语义真实清空蓝图声明区域内的原有方块和临时填充块 |
| `COLLECTING_DEBRIS` | 有可用任务收集无人机时执行一次有界清场；没有收集能力、库存满或卸载受阻的剩余掉落物留在世界，不阻塞建造 |
| `WAITING_DEMOLITION` | 存在可拆方块但缺少拆除无人机，按暂停策略等待玩家处理 |
| `BUILDING` | 正常取料、飞行并交付施工投影 |
| `WAITING_MATERIAL` | 缺料策略为暂停，所有无人机已回站或在安全地点落地 |
| `SOURCE_UNAVAILABLE` | 玩家、下方容器或返还出口暂时不可用；相关无人机立即安全降落并保留任务租约和携带物，来源及加载覆盖恢复后续做 |
| `COMMITTING` | 材料交付结束，区域锁定并执行安静提交 |
| `COMPLETED` | 完整结构提交成功 |
| `COMPLETED_INCOMPLETE` | 存在缺料、按配置跳过的缺工种、不可拆障碍或不可达位置，残缺结构已经自动提交 |
| `STOPPED_PARTIAL` | 玩家取消任务，已交付投影已经提交，拆除结果和部分结构留在世界中 |
| `FAILED` | 格式、世界边界或不可恢复提交错误，需要玩家处理 |

蓝图内部以一份规范化结构快照为准，结构磁盘最终仍使用原版结构 NBT 能表达的内容，不发明另一套只能由无人机读取的世界结构格式。规范数据包含尺寸、调色板、方块位置与 `BlockState`、方块实体 NBT、实体条目、锚点、旋转和镜像；不包含方块或流体计划刻队列，也不保存计划刻剩余时间。

导入层采用适配器，导入后统一转换为上述规范快照：

| 来源 | 兼容要求 |
| --- | --- |
| 原版结构 `.nbt` | 完整读取 `size`、`palette/palettes`、`blocks`、方块实体 NBT 和 `entities`，作为基准格式 |
| Create 蓝图/结构 `.nbt` | 识别其基于原版结构的字段和 Create 附加元数据；可表达内容归一化为原版结构语义，不依赖 Create 的蓝图加农炮运行时代码 |
| Litematica `.litematic` | 读取压缩 NBT、多区域偏移、区域调色板、压缩方块状态数组、方块实体和实体；按确定顺序合并多区域并保留负偏移 |

导入器必须显式报告未知方块、缺失模组、损坏调色板、区域重叠冲突和无法映射的扩展字段，不能静默变成空气。Litematica 或 Create 中超出原版结构语义的信息只可给出警告或拒绝导入，不能假装已经复原。旧 `DataVersion` 通过当前版本的数据修复边界升级；当前项目不因此承诺 Plasticraft 旧存档兼容。

现有 AnvilCraft 结构保存流程若仍省略方块实体 NBT 或固定写出空 `entities`，必须先补齐到完整原版结构语义，否则“内容物和实体复原”没有可靠输入。该工作属于建设系统前置条件。

## 3. 流体封堵、真实拆除、掉落物回收与提交

每个活动任务严格按“权限预检 -> 流体封堵 -> 真实拆除 -> 可选掉落物回收 -> 投影建造”推进。蓝图声明区域内全部原有非空气方块都需要先拆后建，即使原状态已经与蓝图目标完全一致也不复用；Litematica 多区域之间未声明的空隙不扫描。全部可执行拆除完成、永久障碍及按配置保留的障碍已经记入跳过集合后，才允许派发第一个建造操作。拆除阶段不能一边清外墙一边让建设无人机进入内部放置最终施工投影，避免真实世界变化与假碰撞交错后无法判断可达性。

流体不能通过逐格设为空气处理。无限水源、相邻源方块或外部流入可能立刻补回已经清除的位置，因此任务只洪泛扫描蓝图声明区域内的流体，并允许在区域外一格建立临时封堵壳来切断外部流入；绝不继续追踪壳外海洋。内部全部流体格与必要边界壳形成一个有限批次，由建设无人机从玩家或任务站取得真实填充材料，整批填满并切断再生和回流后，拆除无人机才开始拆除该片填充块。

临时填充只选择能够稳定占据流体格、没有方块实体、不会下落或立即自毁的普通实心方块。材料规划先保留完整蓝图本身所需数量，再从剩余候选中选择库存最多的一种。填充块是真实消耗、真实放置并写入任务台账的世界方块，不是假放置或最终施工投影；拆下后成为本任务掉落物，可以由收集无人机回收并再次用于后续封堵或建造。

拆除无人机遵循以下规则：

1. 只执行拆除操作，不从玩家或站点取料，也没有携带物或返还物
2. 切石机到目标的触及距离为 `1` 格，必须存在无阻挡的接近位；到位后瞬间破坏，不显示原版挖掘裂纹或累计进度
3. 破坏语义严格对齐 AnvilCraft 普通铁砧砸中“下方有切石机的方块”路径，而不是玩家挖掘或普通 `destroyBlock`：先拒绝负硬度状态，再使用本体 `BlockMiningEffect.NORMAL` 和 `BreakBlockUtil` 创建正确虚拟工具、结算经验与方块掉落、执行方块的 `spawnAfterBreak` 及多方块移除回调，最后把目标更新为空气。实现时复用本体公开服务或把相同公开 API 组合封装在独立适配器中，避免再维护另一套战利品算法
4. 拆除是真实世界破坏，目标状态立即消失并正常触发相应世界变化；产生的物品、经验和容器内容物全部生成在原位置，拆除无人机不会吸取。每个逻辑方块的瞬间拆除按新版统一规则扣 `2,560 FE`，另结算空中时间和实际飞行距离
5. 基岩、命令方块、屏障等生存模式无法正常破坏的状态标记为永久障碍；它们不阻塞整个拆除阶段，但对应位置的建造操作自动跳过，最终提交也不得覆盖
6. 任务所有者没有权限破坏或放置的受保护位置不属于永久障碍，也不允许自动跳过。规划阶段或执行前发现权限拒绝时，整个任务进入 `WAITING_PERMISSION`；权限恢复后从原台账继续，玩家也可以取消任务
7. 拆除路径按从外向内的可达表面逐层剥离。每次删除真实碰撞后重算局部可达空间，多架拆除无人机通过目标租约避免重复破坏同一格
8. AnvilCraft 大型方块和其他多方块结构使用拆除适配器识别核心及附属 `part`，只执行一次符合该结构正常破坏语义的核心拆除，不能逐个部件重复产生掉落

扫描结果中存在正常可拆方块、但任务没有可用拆除无人机时，才执行暂停/跳过配置。选择“暂停”时进入 `WAITING_DEMOLITION`，报告需要拆除的位置并让其他任务无人机回站或落地；选择“跳过”时把这些障碍保留在世界中，并将对应建造位置记为跳过。基岩等已经确认无法拆除的永久障碍不读取这一配置，也不会使任务停在拆除阶段；其他可拆位置处理完后直接进入建造阶段。任何被保留障碍占据的目标位置都直接跳过，障碍造成的封路还可能使其后方目标因不可达而跳过，任务最终得到 `COMPLETED_INCOMPLETE`。权限拒绝是例外：无论配置为何都必须暂停，不能借缺工种“跳过”间接绕过保护。

拆除产生的每个 `ItemEntity` 都由任务台账关联任务 UUID、来源操作和数量；任务标记必须参与物品实体合并判定，避免任务掉落物与玩家原有掉落物合并后无法区分。没有可用收集无人机时，任务不等待回收，全部掉落物继续留在原位置并照常进入建造。有可用收集无人机时，中央调度器在拆除进行期间即可分配掉落物租约；全部拆除结束后进入一次有界的 `COLLECTING_DEBRIS`，让仍可装载且能够卸货的无人机收取本任务掉落物。九格满载或卸载受阻的无人机保留库存并退出本轮，未领取的剩余掉落物留在世界，随后进入建造。已经被玩家、漏斗或其他实体拿走、烧毁或自然消失的掉落物从台账标记为外部结算，不复制补发。

收集无人机到掉落物一格触及范围内才可吸入，使用自身 `9` 格真实物品库存，正常遵守物品最大堆叠数。一次领取只锁定本任务生成的可拾取掉落物，不收取附近无关物品；库存满或本轮租约完成后返回任务站，经下表面把物品插入下方物流容器，站点不新增材料库存。容器已满时任务收集无人机保留剩余库存并暂停收集，不能把刚收回的施工掉落物再次随地丢出，也不阻塞其他工种继续任务。

采用施工投影可以消除最困难且收益很低的两类问题：建设无人机不需要理解沙子支撑、红石粉附着、活塞更新、锁存器拓扑或模组机器的逐块初始化顺序；真正的目标方块只在所有材料交付完成或玩家取消任务时进入世界。不过，用户看到的“假方块”必须提供对应碰撞，所以建造阶段的空间装配顺序仍然需要规划。

施工过程区分两层投影：

- 未交付投影只负责预览，没有碰撞，无人机可以穿过它抵达结构内部
- 无人机完成一次方块交付后，该位置变为“已施工假方块”，显示目标方块模型并提供目标 `BlockState` 对应的 `VoxelShape` 碰撞

假方块不应真的把世界位置替换成成千上万个占位方块或方块实体。推荐使用按区块段保存的 `ConstructionProjectionIndex`：服务端记录已交付位置和目标状态，客户端只同步附近区块段；渲染器按区块段批量烘焙目标方块模型；世界碰撞查询从同一索引追加虚拟 `VoxelShape`。仓库已有为动态塑料制品扩展 `BlockCollisions` 的窄接口，实现时应抽取或扩展这一索引边界，避免再放置每格一个方块实体。

这一虚拟占位层具有以下硬规则：

1. 玩家、无人机、其他普通实体和塑料实体都与假方块碰撞，服务端是权威，客户端同步同一形状以避免走动回弹
2. 碰撞只表示目标状态的几何；假方块不提供红石信号，不接收随机刻或计划刻，不流动，不创建目标方块实体，不执行 `onPlace`、`neighborChanged`、生存检查或模组机器逻辑
3. 栅栏、墙、门、活板门等依赖相邻状态的形状通过只读“蓝图覆盖视图”计算：已交付位置读取目标状态，其他位置按规划所需读取目标或真实世界状态，不能因为世界里仍是空气而得到错误形状
4. 目标状态本来没有碰撞时，假方块也没有碰撞；例如红石粉、花和多数流体只显示施工投影
5. 新增一块虚拟碰撞前先检查其形状是否与玩家或实体相交。被占据时该操作等待并报告“施工位置被占用”，不能直接把实体封进形状中
6. 路径检测始终查询“真实世界碰撞 + 已交付假方块碰撞 + 临时无人机路线预约”，因此无人机会绕过刚刚完成的假墙、台阶和门体

施工顺序不再分析红石或方块支撑，但必须解决“先封外墙后无法进入内部”的几何装配问题。规划器从完整目标碰撞集合做一次反向可拆解分析：从蓝图外部可达空间开始，反复选择能够在一格触及范围内从外部接近、移除后仍连通的目标块，记录拆解顺序；正向施工使用它的逆序，就会先完成内部、最后从外侧封口。每次真正派发前还要验证放置后的撤离路线，不能只保证蟹钳够得到目标，却把执行无人机封在内部。

拓扑安全是硬约束；在当前所有安全候选中再使用原先的偏好排序：先低层后高层，同层优先远离主要入口/取料方向的位置，再逐渐靠近。多个无人机只从同一安全前沿领取不同目标，并预约目标接近位和撤离段。世界被玩家临时改动后只重算受影响区块段和局部路线，不重新扫描整个蓝图。

全部非跳过建造操作交付后进入完整提交。通用流程如下：

1. 冻结任务派发，确认所有相关区块已加载、材料托管台账闭合、投影索引和蓝图哈希一致
2. 锁定目标区域的施工交互，建立可在异常重启后续做的提交日志
3. 直接写入目标方块状态，内部不发送普通邻居更新、不触发掉落，也不逐块调用玩家放置逻辑
4. 在方块状态齐全后载入方块实体 NBT，再交给大型多方块适配器恢复核心与部件关系
5. 写入流体状态和必要的后续流体刻；实体在方块与方块实体完成后统一生成
6. 移除施工投影碰撞和渲染，向客户端发布完成状态，最后只对结构边界和明确要求的适配器执行受控更新
7. 释放区域锁和观察覆盖租约，提交材料消耗与返还台账；观察无人机按返航、待机及第 6 节能源资格继续或停止自身区块票，任务不能越过观察加载服务直接删除票

完整提交只写入已经通过拆除阶段且没有被跳过的目标位置。拆除成功后又由玩家或其他机器新放入的普通方块不会让提交失败，也不会产生第二次拆除掉落；提交可以强制覆盖这些新变化。不可生存破坏或按配置跳过的原有障碍永远保留，对应建造操作不得在提交阶段偷偷覆盖。权限拒绝尚未解除时任务根本不能进入完整提交；若提交前权限发生变化，则回到 `WAITING_PERMISSION`。已交付目标的虚拟碰撞在提交前已经阻止玩家和实体进入最终实体碰撞形状；无碰撞目标即使与实体重叠也按原版相应状态处理。

玩家主动取消施工不是回滚，而是一次“按当前进度提交”：

1. 立即停止新的流体填充、真实拆除、掉落物租约和建造取料；已经真实拆除的方块保持被拆除，原地掉落物与收集无人机已经取得的库存保持真实状态
2. 已经完成交付并显示为假方块、假流体或实体投影的操作，按与完整提交相同的安静写入流程变成真实内容
3. 建设无人机尚未到达目标的在途资源不计入进度，立即转向来源玩家或任务站返还，不再完成当前交付；返还后无站无人机降落、站属无人机依次回库，尚未取出的资源不发生变化
4. 未交付、被跳过或仍被不可拆障碍占据的位置保持取消瞬间的真实世界状态；若某个已交付投影在取消时已失去写入权限，则不得借部分提交覆盖，而应移除该投影并返还对应托管材料
5. 清除剩余投影和任务租约，结束观察覆盖调度，任务结束为 `STOPPED_PARTIAL`，不再自动恢复或继续；观察无人机自身区块票按其实体/入库状态与第 6 节能源资格独立结算

取消发生在流体封堵或拆除填充块期间时也立即停止，不启动任何额外清理。已经真实放置但还未拆掉的任务填充块原样留在世界；未放置的在途填充材料按普通在途资源立即返还。任务只移除虚拟投影和租约，不能静默删除、无掉落清除或继续拆除这些真实填充块。

因此，一个目标为 `3 x 3 x 3` 圆石的任务在拆除原有石头并完成前两层 `18` 块投影后取消，会立刻得到两层真实圆石；第三层保持空气，已拆石头不会复原。部分提交不保证红石机器可用，也不为玩家主动取消造成的半结构做自动修复。若取消请求到达时任务已进入不可分割的发布点，则先完成正在发布的事务，再以实际已发布进度结束，不能把同一批提交一半回滚。

通用方块不使用假玩家放置。假玩家会触发物品 `useOn`、邻居更新、成就/事件和模组方块初始化，反而破坏保存的红石与机器状态。只有某种方块或实体无法通过公开结构载入接口正确初始化时，才由独立 `PlacementAdapter` 在受控阶段使用 AnvilCraft 假玩家；适配器必须声明消耗、返还、附加位置和更新范围，不能让假玩家成为所有方块的默认路径。

提交保留原版 NBT 中已经存在的红石粉功率、比较器/中继器朝向与锁定、拉杆/按钮状态、稳定的活塞伸出/收回状态以及方块实体配置。结构内部不做一轮无差别邻居更新，因此不会在施工中启动或拆坏机器。提交完成后世界恢复正常规则；如果结构外部供电或邻接环境与保存时不同，红石随后自然变化，这是正常世界行为，不可能由蓝图永久冻结。

原版结构 NBT 不包含计划刻队列，因此不承诺恢复中继器“还剩几刻触发”、流体“还剩几刻流动”或计时器的相位。稳定伸出/收回的活塞可以复原；正在运动中的活塞、移动方块实体和半个游戏刻的瞬态不能在只使用原版结构 NBT的前提下精确续播。验收目标是机器在相同外部环境中从保存的稳定状态恢复并继续正确工作，而不是恢复服务器保存瞬间的调度队列。

“原子提交”定义为玩家和机器观察不到可运行的半成品，不强制任意巨型 Litematica 结构必须在单个服务器 tick 内完成所有内存写入。普通结构可以单 tick 写完；超大结构应在区域锁和完整施工投影遮蔽下分区写入，期间不运行结构内部逻辑，全部写完后在一个发布点移除投影并启用真实结构。这样视觉和玩法上仍是瞬间完成，同时避免单次提交超过服务端 watchdog。玩家愿意接受短暂停顿不等于可以把“任意尺寸”实现成无限内存和无限单 tick 工作量。

Create 的 [`SchematicPrinter`](https://github.com/Creators-of-Create/Create/blob/87b3c6a65fd00c023a07b37b0353144bc7e6a5bf/src/main/java/com/simibubi/create/content/schematics/SchematicPrinter.java) 和 [`BlockHelper.placeSchematicBlock`](https://github.com/Creators-of-Create/Create/blob/87b3c6a65fd00c023a07b37b0353144bc7e6a5bf/src/main/java/com/simibubi/create/foundation/utility/BlockHelper.java) 可参考其结构遍历、易碎方块延后和客户端更新标记，但 Create 蓝图加农炮本身仍是逐块真实放置，也不理解红石依赖，不能直接承担上述安静提交。

## 4. 材料、内容物、流体、实体与多方块

蓝图解析后先生成规范施工操作，而不是简单地认为“每个非空气方块消耗一个同名物品”。操作适配器负责把目标快照映射为所需物品/流体、交付表现、最终写入和返还物：

- 普通方块通常消耗其放置物品，朝向、含水、点亮、功率等状态属性由蓝图恢复，不额外消耗物品
- 临时流体填充块同样必须从真实来源取出，真实放置后再由拆除无人机打成掉落物；被收集并成功卸载的填充材料可以重新参与后续封堵或建造，台账必须防止同一物品在“已放置”和“已回收”状态同时存在
- 门的上半、床的另一半、活塞头和大型机器部件是依附操作，不能重复消耗和重复放置
- 没有常规物品形态的状态必须由专用适配器映射；无法映射时明确列为“不支持的材料操作”，不得免费生成
- 一个无人机一次只抓取一个 `ItemStack` 或一个流体容器；箱内多组内容、机器输入和实体装备可以形成多次交付到同一目标的子操作

内容物必须真实取料，不能把蓝图 NBT 中的物品和流体直接复制进世界。方块实体的容器物品、储罐流体，及有库存实体的内容和装备都进入材料清单。普通配置 NBT、名称和不代表资源的机器设置可由蓝图恢复，但仍需经过类型和权限校验。

所有取出的资源先进入任务托管台账，记录来源玩家或来源容器、原始槽位/流体接口、数量、执行无人机、目标操作和可能的容器返还。无人机携带的是托管资源的实体表现。取消任务时，已经交付的资源随部分提交消耗，尚在途或只完成预约的资源按台账返还；站点失效或提交失败也只返还尚未发布的资源，不能把已经变成真实世界内容的物品再复制一份。

流体方块由无人机取得装满对应流体的桶或注册的兼容流体容器，在一格触及范围内完成投影交付。空桶等容器返还只有在资源转换确认后才结算；交付前取消时恢复原来的装液容器，交付后取消时流体进入部分提交并结算空容器。非整桶的储罐内容按流体能力精确抽取并托管，若来源接口或目标适配器不能表达该数量则暂停并报告，不能四舍五入。

AnvilCraft 大型方块在解析阶段识别核心控制器和全部 `part`：

- 整座多方块折叠成一个以核心位置为锚点的逻辑操作，只消耗核心控制器所代表的正确物品
- 蓝图中的其他 `part` 只用于校验范围、方向、投影和碰撞，不生成重复取料任务
- 核心交付时一次激活整组施工投影碰撞，前提是整组形状均未占据且无人机有撤离路线
- 最终提交由对应适配器先恢复核心数据，再建立部件；不能逐格伪造多个互不关联的控制器

实体使用 `EntityBuildAdapter` 注册表处理“快照类型 -> 可接受物品 -> 投影交付 -> 最终生成 -> 返还物”。目标是支持所有有稳定世界语义、能够由物品表达的持久实体，并明确排除玩家、掉落物、经验球、闪电、投射物、区域效果云以及其他纯瞬态实体。

具体规则如下：

- 船消耗对应木种和类型的船物品；矿车、盔甲架、画、物品展示框等使用各自物品适配器
- 生物可以消耗匹配类型的刷怪蛋，或消耗保存了该类生物的高粘性树脂块
- Plasticraft 塑料实体消耗能够重新放出该实体的塑料制品物品，完整保留玩家模型、材料、颜色、方向和真实内容物；施工阶段只显示静态实体投影，最终提交时再生成具有硬碰撞的塑料实体
- 生物只要求实体类型一致，不要求血量、仇恨、药水效果、AI 记忆等完整运行 NBT 一致；位置、朝向和结构所需的基础姿态仍按蓝图生成
- 有库存、装备或容器内容的实体，其内容仍必须单独真实取料并在生成后装入，不能因为“类型一致”而复制内容
- 树脂块交付后在目标位置显示无 AI 的实体施工投影，并按现有规则生成 `1-3` 个树脂返还物；无人机先把返还物送回任务站下方库存或来源玩家，再领取下一项。真实生物只在最终提交时生成
- 模组实体没有刷怪蛋或标准物品时，以能够保存对应类型的树脂捕获物作为生物类兜底；非生物实体仍必须注册明确适配器

缺料/缺工种策略为“暂停”时，站点无人机依次返回并入库；无站无人机在蓝图范围外安全落地。策略为“跳过”时，缺失建造材料、临时填充材料或拆除能力对应的操作记入跳过集合，其他可执行操作继续，最后自动提交 `COMPLETED_INCOMPLETE`。收集无人机是可选回收能力，缺少它不会触发暂停或跳过；观察无人机是否缺失按第 6 节的区块可用性处理。不可拆永久障碍及其目标位置始终直接跳过，不受该策略控制；权限拒绝则始终暂停。系统只保证完整、未跳过任务的红石和机器复原；选择跳过导致的结构失效属于玩家决定。

首次进入缺料、来源不可用或路径阻塞状态时向任务所有者报告一次，之后在无人机或站点 GUI 中持续显示原因、缺失材料和受阻目标；状态未变化时不重复刷屏。

“来源不可用”与“来源里没有某件物品”不同。玩家离线/跨维度、站点下方容器或能力整体消失等情况属于来源不可用；相关无人机立即停止世界交互，携带原物飞向不在蓝图内的最近预约安全降落点，着地后不再消耗悬浮 FE。任务台账继续保留无人机、租约、携带物和原来源关系，不能因实体所在区块暂时卸载而重新派发同一资源。来源恢复后，调度器先确认或重建无人机落点、来源和后续路线所需的加载覆盖，再唤醒无人机起飞续做。每次任务报价必须预留到安全降落点的能量和路径；执行中落点失效时先重新规划最近可达落点。真正检查到库存中缺少材料时才执行暂停或跳过策略。普通返还物的目标仍存在但库存已满不进入等待：无人机把空桶、树脂等返还物扔在站点或玩家旁边的地面，然后继续任务。收集无人机的九格库存属于批量回收结果，满载卸货失败时保留在机内等待，不套用这一丢弃规则。

## 5. 无人机站、调度与能量

建设无人机站和“无人机库”指同一个方块。站内有 `16` 个可混放建设、拆除、收集和观察无人机的物品槽、`1` 个任务结构磁盘槽和 `1` 个电容器充能槽，共 `18` 个实际槽位，不设置材料库存槽。下表面是唯一物流接口面；下方容器暴露的物品库存和流体能力就是任务站可使用的材料来源。

四个水平侧面各有四条取料显示通道，共 `16` 条，但它们只是服务端分配状态的动态渲染，不是库存槽。站点有电且任务站从下方库存为即将到达的建设无人机原子预约资源后，方块实体渲染器才在对应侧面显示下一件物品略微伸出；无人机进入一格触及范围并抓取后，后一件播放向外滑出的动画。预约物保存在任务托管台账中，不借“渲染槽”制造隐藏库存。普通返还物先经下方接口插回容器；容器存在但已满时，返还物直接作为掉落物生成在站点旁边。拆除和观察无人机不使用取料通道；收集无人机使用独立卸载预约，不能把九格库存伪装成侧面取料渲染槽。

无人机只从顶部入库或出库，取料只接近被分配的水平侧面。顶部泊位是单通道状态机：入库和出库不能同时发生，每 `20 gt` 最多处理一架。入库无人机对准后立即从碰撞实体原子转成已占用站内槽位的无碰撞停泊显示对象，随后播放下沉；出库无人机先从槽位原子转成托管的无碰撞显示对象，升出并确认出口安全后才生成碰撞实体。等待入库的无人机悬停在站点旁的预约等待位，不能瞬间把多架无人机挤进同一位置。站内已满时远程无人机继续等待或在电网内充电，不得覆盖已有无人机物品。

无人机站默认开启转运模式。两个同维度的相邻调度节点每段最多相距 `128` 格，多个站可以组成多跳转运图，使远处站内无人机沿站点链路来到任务站；普通站点网络不支持跨维度调度。远程无人机只在预计能缩短任务完工时间时调度，估算必须包含：

- 各段实际飞行时间和能耗
- 中途站顶部通道每秒一架的排队时间
- 任务站取料侧排队、目标接近位预约和预计剩余操作数
- 无人机当前电量、沿途电网和可能的充电等待
- 各工种的阶段需求、拆除表面并行度、掉落物数量、收集库存与卸载吞吐、观察无人机可覆盖的九区块窗口
- 已经在途及已经分配的本地/远程无人机，避免为了理论并行度调来实际上只会排队的无人机

中央调度器对四个工种使用同一完工时间优化器。本地某类无人机完全没有或数量过少时，可以从同维度远程站借调；本地已有该工种也不阻止借调，只要加入远程无人机后的预计完工时间确实更短。被借调无人机完成任务、清空任务携带物或收集库存并满足返航电量后，沿调度链返回原站，不永久留在任务站。每个施工任务最多同时有 `64` 架四类无人机处于参与状态，相当于四个满载站；其余无人机留站或继续处理其他玩家的任务。

无站建设、拆除和观察无人机只响应到该蓝图任意当前可执行目标的最近直线距离不超过 `128` 格、且确实存在可飞路径的活动蓝图；距离不以蓝图锚点或整个包围盒中心计算。无站建设无人机先飞到任务所有者玩家一格范围内取料，再飞到目标交付，完成后回玩家处领取下一项；无站拆除无人机不需要取料，直接飞向被分配的拆除目标；无站观察无人机领取任务区块覆盖路线。任务站同样不能把单次施工目标分配到自身 `128` 格发现范围之外；远程站点只能通过每段不超过 `128` 格的站点转运把无人机送到任务站，不能绕过任务站到施工目标的范围限制。若某蓝图已由站点认领，这三类无站无人机完全退出该任务。无任务建设和拆除无人机在地面等待；观察无人机按第 6 节规则在有电时离地四格悬停。它们都不得停留在已放置蓝图的包围盒内；放置新蓝图时，范围内的无站无人机即使蓝图尚未启动也会主动撤离。

无站收集无人机不自动参加蓝图中央任务，而是持续扫描自身当前位置 `16` 格范围内可拾取的 `ItemEntity`。每收起一个掉落物后，以新的当前位置重新扫描当前 `16` 格，因此可以沿连续掉落物链逐步移动，但不会先对更远区域做全局搜索。它不吸收经验球；安装的手持磁铁作为无人机组件不消耗原版耐久。没有可拾取目标时落地等待；九格库存装满后必须降落，不再继续吸取。所有者或当前同一 FTB Teams 团队成员进入 `16` 格范围后，无人机按原版背包插入规则卸货；多名合法玩家同时存在时先选所有者，否则选择最近的团队成员。塞不下的物品继续保存在原槽位，之后再次等待可卸载空间，不向无权限玩家卸货。

无人机站拥有与 AnvilCraft 超级电容器相同的内部容量；1.21.1 当前为 `160,000,000 FE`。GUI 使用与塑料成型舱同类的电量条显示当前 FE、容量和额定输入功率。电网和任务系统之间通过独立电力桥隔离：站点内部未满时始终向所在电网请求 `256` 功率，充满后请求 `0`；换算为 FE 的每 tick 充入量读取 AnvilCraft 当前功率转换效率。任务、转运、入库、出库和给无人机充电只消耗站点内部 FE，不直接以“正在工作”为条件向电网请求另一份功率。这样未来本体电网重构时只需替换充电桥。

站点像塑料成型舱一样使用有电和无电两套方块模型；这里的有电表示内部存在可供站点活动使用的 FE，而不是红石信号。无电时显示封闭静止的 `drone_station_off`，不绘制舱门、停泊无人机或四侧取放物动态；有电时显示 `drone_station`，方块实体渲染器再根据服务端同步的泊位、预约物和通道进度绘制所有动态状态。活动中断电时服务端保留槽位、托管对象和动画进度，模型切为无电外观；重新有电后从相同进度继续，不能因渲染切换生成或吞掉无人机与物品。

电容器槽完全复用塑料成型舱的资源充能语义：放入已充电的普通电容器或超级电容器，只有站点剩余容量足以完整接收时才消耗，每 `gt` 最多处理一个，并分别转入对应完整 FE。空电容器优先留在已经腾空的槽位；输入槽仍有剩余堆叠时，返回当前操作玩家背包，背包已满则掉落在站点旁。它不占用下方物流材料库存，也不把电容器当作施工材料。站点被拆下或重新放置时应保留内部 FE。

站点只要存在任一任务、转运、入库或出库活动，每 `gt` 固定从内部扣除 `256 x 当前功率转换效率` FE，不随同时活动数叠加；给各架无人机充入的 FE 再按实际转移量另行扣除。内部 FE 不足时所有站点机械活动保留进度并暂停，站点继续通过电网或电容器补能。站点活动费与无人机自身的悬浮、距离及 `2,560 FE` 瞬时操作费分别结算，不能相互抵扣。

每架无人机的容量直接跟随 AnvilCraft 本体电容器当前容量；1.21.1 当前值为 `8,000,000 FE`，实现时引用本体常量或公开能力，不复制一个容易漂移的魔法数。四类无人机统一使用以下能耗模型：

```text
总消耗 = 256 FE x 空中 gt
       + 256 FE x 实际飞行格数
       + 2,560 FE x 瞬时操作次数
```

空中 `gt` 包含前进、转弯、排队等待和原地悬停；只要无人机没有着地或入库，每 `gt` 都扣 `256 FE`。距离项按服务端实际轨迹长度累计，不按起终点直线距离计算，转弯不单独收费但绕路自然增加距离。落地静止和站内物品状态不扣无人机悬浮 FE。

一次瞬时操作只计算工具在目标处产生独立任务结果的离散世界交互：交付一个施工投影或临时填充块、拆除一个逻辑方块、收起一个 `ItemEntity`、交付一份流体或交付并生成一个实体，各扣 `2,560 FE`。一个掉落物实体无论 `ItemStack` 数量都只算一次；大型多方块按适配器折叠后的逻辑操作计数。取料、向玩家或容器卸货、普通返还，以及入库和出库不收这项费用；它们仍结算实际空中时间和飞行距离，站点动作另收站点活动费。观察加载属于持续操作，不在悬浮费之外额外扣能；站内观察无人机物品既不飞行也不执行瞬时操作，因此自身不扣无人机 FE。

充电遵循以下规则：

- 无人机处在任意有效 AnvilCraft 电网范围内时自动充电，无需入库
- 每架未满电且处在电网内的无人机只为补充自身内部 FE 请求 `8` 功率；悬浮、移动和瞬时操作先扣内部 FE，不因当次动作直接向电网额外请求功率
- 无人机在站内充电时不再单独连接外部电网，而是从站点内部 FE 转移能量；每架并发充电仍以 `8` 功率对应的 FE 速率为基准
- 只有不在电网内且剩余电量不足以继续安全执行时，站属无人机返回可达站点入库充电；充满后重新出库。站点内部 FE 不足时保持入库等待，站点继续用 `256` 功率或电容器补充自身
- 无站无人机在接受任务前若电量不足，直接拒绝任务，不以玩家背包作为充电器，也不开始一趟无法完成的飞行

任务能量报价至少覆盖“当前位置 -> 取料点 -> 目标接近位 -> 下一可靠充电点或原站”的预计空中时间、实际路径长度和瞬时操作数，并加入局部绕行、站点排队、路线等待和返航储备。观察任务还必须报价预计维持窗口的悬停时长；持续观察本身不加价。若沿途存在持续有效电网，可以把它视为充电机会，但分配前仍需保守验证断电后能够到达安全着陆点。剩余电量不足的无人机进入充电计划，不领取物品后才发现无法送达。

## 6. 寻路、并发、区块加载与规模

`128` 格是发现和站点调度单段范围，不是让每架无人机对 `257^3` 个方格做完整 A*。四类无人机共用分层飞行寻路：

1. 先用 `0.5 x 0.5 x 0.5` 碰撞箱做直线扫掠；直达无碰撞时不启动网格搜索
2. 远距离受阻时，在区块段级占用图上寻找共享走廊，只判断该体积是否有可通过连通区域
3. 只在障碍、门洞、取料侧和目标附近的小窗口运行精确三维 A*
4. 最终曲线逐段用真实世界与施工投影 `VoxelShape` 扫掠复核；快照计算结束后服务端主线程再次验证已变化区段
5. 飞行中使用短时路线预约、目标接近位预约和局部速度避让处理其他无人机，而不是为每一对无人机重算全程路径

现有 `AdhesivePathPlanner` 的碰撞扫掠、危险区判断和异步快照思路可以复用，但该类明确服务于约 `16` 格的树脂牵引并带有 `20` 格断裂边界，不能直接扩成无人机的 `128` 格规划器。无人机规划应有独立的长期走廊缓存、局部搜索预算和失效版本号。

建设与拆除交互都要求无人机碰撞箱到目标接近位不超过 `1` 格，并且蟹钳或切石机到目标有无阻挡的交互线段；收集无人机也必须实际飞到掉落物旁才可吸取。任务不是到达目标方块中心；规划器为目标枚举多个相邻接近位。拆除阶段选择当前真实表面可达的位置，建造阶段优先选择放下假碰撞后仍属于外部可达空间的位置。未来工具的触及范围由工具定义声明，不能修改四类现有无人机的一格交互规则。

多机协作由中央任务分配器控制：

- 同一操作只有一个租约：建设租约包含材料、目标、接近位、撤离段和超时，拆除租约独占目标，收集租约独占任务掉落物数量，观察租约独占九区块覆盖窗口和时段
- 狭窄走廊、站点顶部、四侧取料位和封口位置使用时隙预约
- 优先级高的无人机先通过，低优先级无人机在宽处等待，不通过关闭实体碰撞来解决冲突
- 无人机被推离、路线改变或租约超时后，材料仍由台账追踪，目标可以重新分配但不能重复消耗
- 多架空闲无人机可以在地面物理堆放；飞行避让只影响导航，不改变 `0.5` 碰撞箱

加载覆盖由观察无人机独占，蓝图和其他工种不再隐式加载大面积世界。加载单位统一为 `ChunkPos` 表示的完整高度区块柱；一份观察覆盖是以观察无人机或站点所在区块为中心，连同水平八邻区形成的 `3 x 3` 九个区块，九个区块都必须取得能够让实体和方块实体正常运行的实体刻级区块票，不再设置任何 Y 向逻辑窗口：

- 已部署或活动蓝图本身不建立加载票；投影、台账和提交日志保存在世界级数据中，对应区块重新活动时再恢复碰撞与渲染
- 建设、拆除和收集无人机即使正在执行任务也不建立加载票，只能在玩家、其他加载器或观察无人机已经保持实体刻的区块内移动和工作
- 世界中的观察无人机只在自身当前维度加载以所在区块为中心的九个完整区块；地下、高空和地表目标只要 X/Z 落在这九个区块内就使用同一覆盖
- 观察无人机跨越区块边界时，先申请并确认新中心的九区块覆盖，再释放旧中心不再重叠的区块；依赖它的工人未进入新覆盖前不得越过旧覆盖边缘
- 无任务的观察无人机只要有电，就起飞并让碰撞箱底面保持在当前 X/Z 下方最近稳定、非流体碰撞顶面之上 `4` 格处；目标高度受阻时在附近寻找安全点，找不到则保持落地。执行观察任务时不受离地四格限制，可以停在调度器选定的任意无碰撞安全位置
- 世界观察无人机必须始终保留安全降落电量。达到降落储备前先停止领取新覆盖路线；能交接时把依赖工人移交给其他观察或外部加载来源，不能交接时先让依赖工人降落，随后自身立即安全降落并释放区块票。落地和空电观察无人机都不加载区块
- 站点的 `16` 个无人机槽中至少有一架带可用电量的观察无人机物品时，以站点所在区块为中心建立同样的九区块覆盖，存放多架不叠加范围。观察无人机为空电、但站点内部 FE 足以给它充电时，站点先完成充电资格校验再建立覆盖；两者都无电时不加载。普通箱子和玩家背包中的观察无人机物品不加载
- 最后一架具备加载资格的观察无人机出库时，站点覆盖先与该实体的新覆盖原子交接再释放；观察无人机入库时执行相反交接。交接期间不能让站点、无人机或跟随工人停止刻
- 观察实体与站点的覆盖中心、维度、能源资格和引用计数保存在世界级加载索引中。服务器启动时由该索引先恢复符合资格的区块票，再等待实体或方块实体加载后校验；失效记录立即撤票，不能依赖尚未加载的站点或无人机自己唤醒自己

观察覆盖只存在于其当前维度，不跨维度映射，也不为其他维度建立远程票。系统不设置额外的每名玩家或每维度观察无人机数量上限；每架符合资格的观察实体或每个符合资格的站点各提供一份九区块覆盖，重叠区块用引用计数合并。单个蓝图任务既有的 `64` 架参与无人机上限仍然有效，它不是观察票的独立全局上限。

中央任务必须支持执行中增量插入、移动和释放观察覆盖任务，不能在启动时一次性固定全部路线并永久加载：

1. 每次派发前查询取料点、路线和目标涉及的区块当前是否已由玩家、观察无人机或其他原版/模组来源保持实体刻；已有覆盖时直接利用，不额外占用观察无人机
2. 覆盖即将消失或下一项进入未覆盖区块时，把观察任务插入当前计划，先让观察无人机到达并建立九区块窗口，再允许其他工种进入
3. 所有依赖工人离开后即可释放该观察任务，让无人机移动到下一窗口、返站或恢复四格悬停；自然加载后来出现时也可以提前释放冗余观察任务
4. 任务站所在区块同样必须处于实体刻窗口内，才能执行库存访问、任务协调、入库、出库和远程转运。站内已有具备加载资格的观察无人机时可自加载；否则先安排其他观察无人机覆盖该站，再调度其中的建设、拆除或收集无人机
5. 可用观察无人机不足时不直接失败。调度器收缩后续并行前沿，重排尚未开始的操作，让其他无人机结队跟随观察无人机移动；必要时让同一架观察无人机在安全停靠群与下一工作区之间往返搬运窗口
6. 完全没有可用观察无人机且下一项所需区块也没有其他有效加载来源时，任务进入 `WAITING_OBSERVER`；任一外部加载来源出现或观察无人机可用后立即重新规划

来源不可用时，普通工种无人机在现有观察或外部覆盖释放前立即飞到预约安全点降落；着地后观察窗口可以转去执行其他路线，使该实体随区块卸载而停止刻。任务台账继续保留其 UUID、落点、租约和携带物。来源恢复后，调度器先用观察无人机或外部来源重新覆盖落点、来源和后续路线，确认实体重新加载且台账一致后才允许起飞继续；不能因为实体暂时未加载就复制其携带物或把租约发给另一架无人机。

蓝图不设置一个类似 `128^3` 的玩法尺寸上限；要接近 Litematica 的大结构体验，内部必须按区块段使用局部调色板、稀疏位图、交付位集和增量材料统计，客户端只接收可见区段与进度差量，投影按区块段批量建网格。无限放置指不人为限制非活动蓝图数量，实际仍受世界边界、建筑高度、存档空间、内存和服务器管理配置约束，损坏文件声明的极端尺寸必须在分配内存前拒绝。

任务、流体封堵、拆除进度、任务掉落物、投影、观察覆盖计划和提交日志保存在世界级持久数据中；无人机实体只同步渲染必需的旋翼数据、工具、携带物或收集库存、动作、能量摘要和短期状态。服务端异常重启后按日志恢复：已经真实放置的填充块和已经真实拆除的位置保持结果且不会重复派发，尚未发布的托管资源继续由台账持有；已进入发布点则完成剩余分区并只发布一次。不能出现已经拆除的方块被任务凭空复原，也不能出现真实半结构已经运行、任务却回到取料阶段的状态。

实现边界应至少分为：结构格式与规范快照、中央任务与材料台账、所有权服务与独立 FTB Teams 适配器、工具能力注册、流体封堵规划、拆除扫描与本体破坏适配器、任务掉落物追踪、施工投影索引、装配顺序规划、飞行与观察覆盖规划、站点综合调度、电力充电桥、方块/实体适配器、安静提交服务，以及纯客户端的无人机/投影/菜单渲染。NeoForge 注册放在 `init`，客户端代码放在 `client`；公共任务逻辑不引用渲染类或 FTB Teams API。未来 26.1.2 迁移时只替换本体电网、结构 API、区块票 API 和注册适配层，不改任务语义或网络字段既有顺序。

## 7. 验收基线

后续实现至少需要覆盖以下验收场景：

- 四种配方只替换蟹钳位置的工具；两个不同玩家模型、颜色和材质的螺旋桨经过合成、实体化、入库、出库和铁砧锤回收后完整往返，任意一个耐热螺旋桨即可防火
- 四种无人机分别显示 Plasticraft 风格统一的定制可动蟹钳、切石机、磁铁和望远镜附件，不直接缩放配方输入模型；物品栏、手持、掉落物和物品展示框都渲染与实体一致的完整三维外观
- 八架任意工种无人机可在一格内自由堆放，玩家可站在无人机上；飞行中的多机不会在门洞、拆除表面、掉落物区、观察接力点、取料侧和顶部泊位互相堵死
- 蓝图声明区域内原本与目标相同的方块也先拆后建；拆除瞬间完成，其经验、战利品、多方块回调和不可破坏判定与 AnvilCraft 普通铁砧砸切石机上方方块一致，拆除无人机始终不吸取物品
- 缺少拆除无人机时“暂停”会等待并报告，“跳过”会保留障碍后继续；基岩等永久障碍无论配置如何都不会阻塞整个任务，其目标位置直接跳过
- 领地或权限拒绝无论配置如何都进入 `WAITING_PERMISSION`，恢复授权后续做；任务不能通过跳过或最终强制覆盖绕过保护
- 多个相邻水源和蓝图边界外持续流入的水先被有限临时填充集合一次封住，再拆掉填充块；任务不会逐格清水后被无限水源永远补回，也不会无边界追踪整片海洋
- 流体封堵中途取消会立刻停止；已真实放下的填充块原样留在世界，未放置的在途材料返还，不出现取消后继续清理或无掉落删除
- 没有收集无人机时，拆除掉落物留在原处且不阻塞施工；有本地或远程收集无人机时，只收本任务掉落物，九格库存和卸载失败经过实体化、入库、重启后不丢失或复制
- 无站收集无人机能沿连续掉落物在每次拾取后重新扫描当前 `16` 格；库存满后降落，只向所有者或当前 FTB Teams 团队成员转入背包可容纳的物品，不收经验也不损耗磁铁耐久
